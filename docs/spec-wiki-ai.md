# 위키 검색 AI 개발 명세서

- 작성일: 2026-07-07
- 상태: 초안 (구현 착수 기준 문서)
- 대상 코드: `apps/backend/app/lib/wiki-rag.js`, `apps/backend/app/railway-gateway-server.js`, `apps/desktop/src/App.tsx`
- 자매 문서: [spec-calendar-ai.md](spec-calendar-ai.md) — 임베딩 인프라(§4)와 품질 검증 체계(§5)의 골격을 공유한다

---

## 1. 기획의도

**내 지식 검색 비서.** iCloud LLM-Wiki 마크다운 문서를 근거로 인용하며 지식 질문에 답한다. "UniPort 시스템 구조가 뭐야?", "배포 절차 정리해줘."

**비목표 (하면 안 되는 것):**
- 일정/할일 답변 — 캘린더 AI의 영역. task/calendar source가 섞이면 버그
- 웹 검색, 문서에 없는 내용의 추론 — 위키에 없으면 "없다"고 말한다
- 쓰기 작업 — 위키 AI는 읽기 전용

**판정 기준:** 답변의 모든 주장이 검색된 위키 청크에 실제로 있는가(충실성). 이전 100회 리포트에서 "아웃소싱 에이전트", "위키가 개발한 에이전트" 같은 원문에 없는 왜곡이 다수 발견된 것이 이 기능의 대표 실패 사례다. **답변 길이(350자)·통과율 같은 대리 지표를 목표로 삼지 않는다.**

---

## 2. 파이프라인

구조는 현행 유지. 아래 §3의 인덱싱·점수식·프롬프트·실패 처리만 교체/강화한다.

```
[위키 탭 질문 입력]
  → POST /api/wiki/search              — RAG 검색, sources 반환
  → POST /api/chat/stream (view: wiki, agent: wiki-curator)
      컨텍스트 = 검색된 청크 상위 6개 (문서 경로 + 제목 + 원문)
  → SSE 스트리밍, done 이벤트에 { text, sources, llm, retrieval, answerMode }
```

- 라우팅은 화면 기준: 위키 탭 입력은 전부 이 경로. 캘린더 데이터는 절대 컨텍스트에 넣지 않는다.
- 근거 데이터: iCloud LLM-Wiki 파일 기반 RAG (`retrieval: "wiki-files"`)가 항상 1순위.

## 3. 구성 요소별 명세

### 3.1 인덱싱 (wiki-rag.js)

- **청킹:** 마크다운 헤딩(`##`) 경계 우선 분할, 청크 400~800자, 인접 청크 80자 오버랩. 각 청크에 `{ path, title, headingPath, text }` 메타 유지.
- **임베딩:** 현행 `createEmbedding`(해시 벡터 — 단어 겹침만 보는 가짜 임베딩)을 Ollama 임베딩(§4)으로 교체.
- **인덱스 캐시:** `{ 파일 mtime, 임베딩 모델명 }` 키로 디스크 캐시. 파일 변경 시 해당 파일 청크만 재계산. 콜드 빌드 ≤ 30s.

### 3.2 검색 점수

- 최종 점수: `0.60 × 임베딩 코사인 + 0.25 × 제목 매칭 + 0.15 × 키워드 겹침` (현행 0.42/0.35/0.23에서 임베딩 비중 상향 — 진짜 임베딩 전제).
- 상위 6개 청크를 생성 컨텍스트로 전달.

### 3.3 검색 실패 처리 (신규)

- 최고 점수가 임계값(초기값 0.35, 골든셋으로 튜닝) 미만이면 **LLM을 호출하지 않고** "위키에서 관련 문서를 찾지 못했다 + 가장 가까운 문서 3개 제목"을 반환한다. `answerMode: "no-retrieval"`.
- 낮은 점수 청크로 생성을 강행하는 것이 환각의 주 원인이므로 금지.

### 3.4 생성 (wiki-curator 프롬프트)

- "제공된 위키 청크에만 근거해 답하라. 청크에 없는 시스템·역할·관계를 만들어내지 마라."
- "각 문단 끝에 근거 문서를 `(출처: 파일명 § 섹션)` 형식으로 표기하라."
- "질문이 문서 범위를 벗어나면, 아는 부분까지 답하고 나머지는 위키에 없다고 말하라."
- **길이 강제 없음** (현행 350자 기준 폐지). 모델: qwen2.5:7b (캘린더 AI와 동일 인스턴스).

### 3.5 응답 변화 (railway-gateway-server.js)

| 항목 | 변경 |
|---|---|
| `/api/wiki/search` | 점수식 교체, 임계값 미만 시 `answerMode: "no-retrieval"` |
| `/api/chat/stream` | done 이벤트에 `answerMode: "llm" | "no-retrieval"` 추가 |

## 4. 임베딩 인프라 (캘린더 AI와 공유)

- **모델:** Mac mini Ollama에 `bge-m3` (1순위, 한국어 강함) 또는 `nomic-embed-text` (2순위, 경량). `POST {OLLAMA}/api/embeddings`.
- **모듈:** `apps/backend/app/lib/embeddings.js` 신규 (캘린더 AI와 동일 모듈 사용).
  - `embedText(text, { model, fetchImpl })` → `number[]`
  - `embedBatch(texts)` — 위키 인덱싱용
  - Ollama 미응답 시 현행 해시 벡터로 **폴백**하되 `embeddingModel: "hash-fallback"`으로 표기. 폴백률은 품질 지표로 집계.

## 5. 품질 검증 체계

### 5.1 두 계층 분리

**계층 1 — 하드 어서션 (결정적, 1건이라도 실패 시 즉시 실패):**

- HTTP 200, `/api/wiki/search` + `/api/chat/stream`(view: wiki) 호출 건수 정확, `/api/assistant/ask` 호출 0건
- `retrieval === "wiki-files"`, `llm.provider === "local-llm"` (no-retrieval 응답 제외)
- sources는 전부 위키 파일 경로 — task/calendar/chat 오염 금지
- done 이벤트 스키마 유효성 (`answerMode` 존재)

**계층 2 — 품질 게이트 (확률적, 개별 실패는 기록만, 런 전체 집계로 판정):**

| 지표 | 기준 (100회 런) |
|---|---|
| `answerMode === "llm"` 비율 (관련 문서가 존재하는 질문 기준) | ≥ 95% |
| 답변 공백제거 길이 ≥ 200자 | ≥ 90% (350자 하드컷 폐지) |
| 출처 표기 `(출처: …)` 포함률 | ≥ 90% |
| 한국어 외 문자 혼입 (중국어 등) | ≤ 2% |
| 임베딩 해시 폴백률 | ≤ 1% |
| 골든셋 사실 포함률 (§5.2) | ≥ 90% |
| 골든셋 환각 검사 (`mustNotInclude` 위반) | ≤ 5% |

기준 미달 시 런 실패. **개별 질문의 LLM 출력에 대한 `assert`는 두지 않는다.**

### 5.2 골든셋

- 위치: `apps/backend/tests/fixtures/golden-set.json` (캘린더 AI와 같은 파일, `kind: "wiki"`)
- 문항의 목표 품질 기준과 골든셋 변환 예시는 **부록 A** 참조.
- **15문항**: 위키 문서에 실재하는 기대 사실 + 대표 왜곡 표현을 명시.

```jsonc
{
  "kind": "wiki",
  "question": "UniPort 시스템 구조를 설명해줘",
  "mustIncludeFacts": ["Hermes", "Railway"],
  "mustNotInclude": ["아웃소싱 에이전트"],        // 과거 실제 발생한 환각 표현을 회귀 검사로 축적
  "expectedRetrieval": "wiki-files",
  "expectedFirstSourcePath": "2_wiki/UniPort-시스템구조.md"
}
```

- **의미 검색 검증 문항 포함**: 문서 제목과 단어가 겹치지 않는 질문("릴리즈는 어떻게 해?" → 배포 문서 매칭)을 최소 3문항 넣어 임베딩 교체 효과를 직접 측정한다.
- 검색 임계값(§3.3)이 정상 질문을 걸러내지 않는지 확인하는 문항과, 위키에 없는 주제 질문("김치찌개 레시피") → `no-retrieval` 기대 문항을 각 2개 포함.

### 5.3 테스트 피라미드

| 레벨 | 파일 | 실행 시점 | 내용 |
|---|---|---|---|
| 유닛 | `wiki-fallback.test.cjs` (현행 확장) | 매 커밋 | 청킹 경계, 점수식, 임계값 분기, mtime 캐시 무효화, 폴백 표기 |
| API 통합 | `tests/api-golden.test.cjs` (신규, 캘린더와 공용) | 매 커밋 (LLM 필요 시 로컬) | 골든셋 15문항 fetch 직접 호출, 계층 1+2 검증 |

## 6. 상세 개발 로드맵

캘린더 AI 마일스톤(M1~M5)과 같은 트랙에서 진행한다. 위키 AI는 M1(캘린더 후처리 정리)과 M5(일정 입력)에는 몫이 없고, **M2~M4에서 아래 작업을 수행한다.** `embeddings.js` 공유 모듈은 캘린더 트랙(M2 작업 2.1~2.2)에서 만들어지므로 그 완료가 선행 조건이다.

```
[캘린더 M2 작업 2.1~2.2: embeddings.js] ──→ W2 인덱싱·검색 교체 ──→ W3 골든셋·테스트 ──→ W4 프롬프트·7b 측정
                                              (0.5d)                  (0.5d)               (0.5d)
```

**공통 규칙:** 각 마일스톤 종료 시 골든셋 통과율·게이트 지표를 기록한다. **측정 없이 다음 단계로 넘어가지 않는다.**

### W2 — 인덱싱·검색 교체 (M2 내, 0.5일)

| # | 작업 | 대상 | 완료 기준 (DoD) |
|---|---|---|---|
| 2.1 | 헤딩 기반 청킹: `##` 경계 우선 분할, 400~800자, 80자 오버랩, `headingPath` 메타 | `wiki-rag.js` 인덱싱부 | 유닛: 헤딩 있는/없는/초장문 문서 3케이스에서 청크 경계·오버랩 검증 |
| 2.2 | `createEmbedding`(해시 벡터) → `embeddings.js` 호출로 교체. 점수식 `0.60×임베딩 + 0.25×제목 + 0.15×키워드` | `wiki-rag.js:30, 186~200` | 유닛: 점수 합성 로직 (임베딩 mock). 해시 함수는 폴백 전용으로만 잔존 |

### 리스크와 대응

| 리스크 | 신호 | 대응 |
|---|---|---|
| 임계값 0.35 오탐 (정상 질문 차단) | 골든셋 오탐 검사 문항 실패 | 임계값을 0.05 단위로 낮추며 no-retrieval 문항과 동시 통과 지점 탐색 |
| 청킹 후 컨텍스트 파편화 (답변이 얕아짐) | 골든셋 사실 포함률 하락 | 오버랩 80→150자 확대, 또는 같은 문서의 인접 청크 병합 전달 |
| 콜드 빌드 30s 초과 | 위키 문서 증가 | `embedBatch` 병렬화(4개 단위), 서버 기동 시 백그라운드 빌드 + 완료 전 해시 폴백 |
| 출처 표기를 모델이 누락 | 표기율 < 90% | 컨텍스트 청크에 `[1] [2]` 번호를 붙이고 번호 인용으로 단순화 |

## 7. 성능 목표

| 항목 | 목표 (p95) | 현재 실측 (2026-07-07 리포트) |
|---|---|---|
| 검색+스트림 완료 | ≤ 10s | avg 3.8s / max 5.7s (3b 기준 — 7b 전환 후 재측정) |
| 위키 인덱스 콜드 빌드 | ≤ 30s | 미측정 |
| 질문 임베딩 1회 | ≤ 100ms | 미측정 |

7b 전환으로 지연이 목표를 넘으면 컨텍스트 청크 수(6→4)와 num_predict 상한으로 조정하고, 그래도 넘으면 3b/7b 중 골든셋 점수-지연 트레이드오프를 측정해 결정한다.

## 부록 A — 질문·답변 예시 (목표 품질 기준)

아래 예시가 이 명세서가 목표하는 답변 품질의 기준이며, 골든셋(§5.2)의 원형이다. "현재"는 2026-07-07 라이브 100회 리포트 실측이다.

### A.1 일반 지식 질문

**Q: "UniPort 시스템 구조를 설명해줘"**

❌ **현재 (원문에 없는 왜곡 — 대표 실패 사례):**

> UniPort 시스템 구조는 Hermes와 **아웃소싱 에이전트**가 참여하는 **복잡한 네트워크 구조**를 통해 이루어진다.

✅ **목표** — 청크에 있는 내용만 + 문단별 출처 표기:

> UniPort 시스템은 크게 세 층으로 구성됩니다.
>
> **커뮤니케이션 층** — 텔레그램 팀 채널과 디스코드 @pm 봇이 사람의 요청을 받는 입구입니다 (출처: UniPort-시스템구조.md § 채널 구조).
>
> **두뇌 층** — iCloud의 LLM Wiki가 프로젝트 지식의 단일 저장소 역할을 하고, Hermes 에이전트가 이 위키와 스킬을 읽어 작업을 수행합니다 (출처: UniPort-시스템구조.md § LLM Wiki).
>
> **실행 층** — Mac mini 로컬 runtime이 LLM 추론을, Railway 백엔드가 DB와 API를 담당하며, 콘텐츠 수정은 프리뷰 검증을 거쳐 개발 반영으로 이어집니다 (출처: UniPort-시스템구조.md § 개발 반영 경로).
>
> 문서에 명시된 핵심 리스크는 Mac mini 단일 장비 의존입니다 — 이 장비가 내려가면 로컬 LLM 답변 경로 전체가 멈춥니다.

- 골든셋 변환: `mustIncludeFacts: ["Hermes", "Railway", "Mac mini"]`, `mustNotInclude: ["아웃소싱"]` (과거 실제 환각을 회귀 검사로 축적), `expectedFirstSourcePath: "2_wiki/UniPort-시스템구조.md"`

### A.2 의미 검색 (단어가 안 겹치는 질문 — 임베딩 교체 검증용)

**Q: "새 기능 만들면 실제 앱에 어떻게 올려?"**

- 현재 해시 벡터: "올려" 같은 단어가 문서에 없으면 매칭 실패 가능 (단어 겹침만 계산)
- ✅ bge-m3 임베딩: "개발 반영 경로" 문서와 **의미로** 매칭:

> 위키 기준으로 반영 경로는 4단계입니다: 수정 → 백업 → 프리뷰 이미지 검증 → 앱 반영 (출처: UniPort-개발반영.md § 반영 절차). 특히 백업과 프리뷰 검증을 건너뛰지 않는 것이 문서에서 강조하는 지점입니다.

- 골든셋에 이런 문항을 최소 3개 포함해 임베딩 교체의 효과를 직접 측정한다 (§5.2).

### A.3 위키에 없는 질문 (no-retrieval — LLM 호출 안 함)

**Q: "김치찌개 맛있게 끓이는 법 알려줘"**

✅ **목표** — 최고 검색 점수가 임계값 0.35 미만 → LLM 미호출, `answerMode: "no-retrieval"`:

> 위키에서 이 질문과 관련된 문서를 찾지 못했어요. 가장 가까운 문서는 「UniPort-시스템구조」, 「UniPort-개발반영」, 「Mac-mini-운영」인데 질문과는 거리가 있어 보여요. 위키에 있는 내용으로 다시 질문해주시겠어요?

- 낮은 점수 청크로 생성을 강행하면 A.1의 ❌ 같은 환각이 나오므로, 이 경우 생성 자체를 하지 않는 것이 §3.3 규칙이다.
- 골든셋에 no-retrieval 기대 문항 2개, 반대로 임계값이 정상 질문을 걸러내지 않는지 확인하는 문항 2개를 포함한다.
